# RWKV 更新说明

根据实际变更撰写面向用户或团队的发布草稿，并提供可追溯的证据。

## 流程

1. 明确目标读者、版本和 Git 范围。版本或起止引用未提供时先查看已有标签与近期日志，必要时询问。不要编造版本、发布日期或默认使用不确定的范围。
2. 读取适用的项目说明和已有 changelog，沿用项目格式。查看范围内的提交、文件差异及影响用户行为的实现；仅凭提交标题不足以证明功能已经完成。
3. 合并重复提交和修复后撤回的内容。按需要组织为新增、修复、行为变化、迁移事项；没有内容的分类省略。
4. 每条描述具体改变、受影响对象及必要操作。仅在代码、配置或文档中有证据时写入不兼容变更或迁移要求。
5. 性能数字、支持平台、部署结果和测试通过情况必须有来源。无法确认的事项单独列为待确认，不写成已经完成。
6. 根据用户要求输出聊天草稿或更新本地文档。只有明确授权发布时才创建远程 release、推送标签或向他人发送通知。

## 输出

- 开头写版本和范围；未知的版本保持待定，不擅自补日期。
- 更新条目用短句说明用户能感受到的变化。
- 技术读者需要时附提交短哈希、PR 或文件链接，链接必须来自实际记录。
- 将必要的迁移操作和验证限制放在对应变更附近。

示例：`$rwkv-release-notes 根据 v1.2.0 到 v1.3.0 的差异生成面向内部用户的更新说明。`
